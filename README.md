# SkipLine - Smart Canteen 
## By Devansh Pokhariya

A full-stack mess/canteen ordering system with a prepaid **points wallet**.
Branded **SkipLine**: _Smart Canteen Management, Without the Queue._

- The app opens on a **landing page** → **Login / Register** → the workspace.
- **Students** can **self-register** with an admin-issued **verification code**,
  get a monthly points allowance, order from the menu (subject to a daily spend
  limit), and pick up once the kitchen marks the order ready.
- **Kitchen staff (chef)** move orders through the kitchen and mark dishes sold out.
- **Admin (mess owner)** adds people (including bulk import from Excel), manages
  the menu, **generates and manages verification codes**, adjusts points, and
  views reports.

Registration is gated: a student can only create an account with a valid,
unused verification code generated by an admin. Staff and admin accounts are
still created by the mess office / seed script.

Stack: React + Vite (frontend), Node + Express + MongoDB/Mongoose (backend), JWT auth.

## 1. Prerequisites

- **Node.js 18+**
- **MongoDB** running locally (you already have `mongosh` / the community server).
  The default connection is `mongodb://127.0.0.1:27017/smart_canteen`.
  When you later move to **MongoDB Compass / Atlas**, you only change one line in
  `.env` - no code changes.

## 2. Backend setup

```bash
cd backend
cp .env.example .env        # then edit .env (see below)
npm install
npm run seed                # creates the admin, a demo chef + student, and a sample menu
npm run dev                 # starts the API on http://localhost:4000
```

### Key settings in `backend/.env`

| Variable | Meaning | Default |
| | -- | - |
| `MONGO_URI` | Mongo connection string. Swap in your Compass/Atlas URI later. | `mongodb://127.0.0.1:27017/smart_canteen` |
| `JWT_SECRET` | Change to a long random string. | - |
| `MESS_NAME` | Shown across the app. | `SkipLine` |
| `MONTHLY_ALLOWANCE` | Points each student gets per month. | `8000` |
| `DAILY_LIMIT` | Max a student can spend in one day. | `450` |
| `DEFAULT_STUDENT_PASSWORD` | Fallback password for uploaded students. | `canteen@123` |
| `ADMIN_LOGIN` / `ADMIN_PASSWORD` | The seeded mess-owner account.

After `npm run seed` you can sign in with:

> The chef and student are seeded with **must-reset-password** on, so the first
> login walks them through choosing a new password. The admin password comes
> straight from `.env`, so change `ADMIN_PASSWORD` before seeding in production.

`npm run seed` also prints **three ready-to-use verification codes** (e.g.
`SKP-7K9XXX`). Use one on the Register screen to create a student account, or
generate more from **Admin → Codes**.

### Adding real admins manually (in the database)

Admins are meant to be added by you directly. Either edit `.env` and re-run
`npm run seed` (idempotent - it skips accounts that already exist), or insert a
user document with `role: "admin"` and a bcrypt password hash via Compass/mongosh.

## 4. Self-service registration & verification codes

The app now opens on a **landing page**. From there:

- **Login** - existing students / chef / admin sign in with their ID + password.
- **Create Account** - a student registers themselves.

**Registration form** (all fields validated on the client _and_ re-validated on
the server - the client checks are only for fast, friendly feedback):
On success the student is signed in automatically and lands on their dashboard.
The **login ID** is derived from the email local-part (the reg number), so they
sign in next time with e.g. `24bca0014`.

**How verification codes work**

- Only an **admin** can create codes (**Admin → Codes → Generate code**), with an
  optional 7- or 30-day expiry.
- Codes are generated with **crypto-secure randomness** in the form `SKP-XXXXXX`
  (unambiguous alphabet, e.g. `SKP-7K9X2M`) - never predictable.
- Each code is **single-use**: the moment a registration succeeds the code is
  atomically marked _used_ and can't be reused. Admins can also deactivate or
  delete codes.
- The full list of codes is **never** exposed to students - the backend only ever
  checks a submitted code and returns valid/invalid.


## 5. How the points system works

- On the first activity in a new calendar month, each student's balance is
  **reset to the monthly allowance** (use-it-or-lose-it - the standard mess model).
  Admins can also force this for everyone with **People → Run allocation**.
- Placing an order is blocked by the server if it exceeds either the **balance**
  or the **remaining daily limit** (`DAILY_LIMIT`, default ₹450). Prices are
  re-read from the database on every order so the client can't tamper with them.
- Cancelling an order **refunds** the points.
- Admins can manually credit/deduct a student's points (People → coin icon).

> Points and rupees are treated 1:1. If you want a different daily-limit meaning
> (e.g. a mess-wide cap rather than per student), change the check in
> `backend/src/routes/orders.routes.js` and the `DAILY_LIMIT` value.

## 6. Bulk-importing students from Excel

**People → Import Excel.** Download the template from inside that dialog, or use a
sheet whose first row has headers. Recognised columns (spelling is flexible):

- **Name** (or `Full Name`, `Student Name`) - required
- **LoginId** (or `Reg No`, `ID`, `Roll No`, `Registration No`) - required
- **Email** (or `Mail`)
- **Block** (or `Hostel`)
- **Phone** (or `Mobile`, `Contact`)
- **Password** (optional - falls back to `DEFAULT_STUDENT_PASSWORD`)

Every imported student is created with **must-reset-password**, so they set their
own password on first login. After import you get a list of the temporary
passwords to hand out. Rows missing a name/ID, or whose ID already exists, are
skipped and reported.

## 7. Password resets

- **First login:** anyone created with a temporary password is walked through
  setting their own before they can use the app.
- **Self-service:** every role has **Account → Change password**.
- **Locked out:** an admin can reset any user's password to a fresh temporary one
  (People → key icon), which the user then changes on next login. This is the
  no-email recovery path.
